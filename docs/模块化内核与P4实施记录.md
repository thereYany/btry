# 模块化内核与 P4 实施记录（第一阶段：Spring Modulith 接入）

> 日期：2026-11-18　范围：P4 第一阶段——把模块边界变成可执行门禁，不改包结构
> 结论：Spring Modulith 2.1.2 已接入，`mvn test` 自动验证模块依赖图；发现并冻结 1 个既有循环
> （commerce ↔ course ↔ learning，由 `*.api` 契约造成），用"循环棘轮"防止架构继续退化，并生成模块图文档。

## 1. 为什么用 Modulith

- 现有 9 条 ArchUnit 规则是**包级**约束（例如 payment 不得依赖 order），但回答不了"模块之间有没有循环、谁依赖谁"；
- Spring Modulith 以"模块依赖图"为一等公民：能检测循环、生成模块文档、后续可做事件发布/模块级 allowedDependencies；
- 2.1.2 对齐 Spring Boot 4.1（本项目当前底座），`ApplicationModules.of(...)` 只做静态分析，无运行时侵入。

## 2. 模块边界（as-built）

模块 = `com.wherelee.edu.modules` 的直接子包：

| 模块 | 职责 | 直接依赖（当前） |
|---|---|---|
| `platform` | 共享内核：租户、追踪、告警、存储、AOP、通用配置 | 无业务依赖（仅自身） |
| `identity` | 账号、登录、JWT、邀请、角色权限（RBAC） | platform |
| `course` | 系列/章节/视频、课程治理、教师端内容 | platform, identity, commerce, learning |
| `commerce` | 订单、支付、退款、权益、对账 | platform, course |
| `learning` | 学习空间、进度、播放日志 | platform, course, commerce |
| `operations` | 运营后台（订单/用户/课程/对账/角色管理） | platform, identity, course, commerce, learning |

边界规则（ArchUnit 已覆盖部分，Modulith 图为准）：

- `platform` 不得依赖任何业务模块；
- `identity` 只依赖 `platform`；
- `learning` 只能依赖 `course.api` / `commerce.api` 契约，不得依赖实现与 `identity`/`operations`；
- `commerce` 不得依赖 `operations`；`payment` 子包不得依赖 `order`/`entitlement`；
- `operations` 只通过各模块 api / 服务访问，不直接碰存储实现。

## 3. 现状依赖图与循环

模块图（快照）：[`docs/generated/modulith/components.puml`](generated/modulith/components.puml)，
全量模块文档：[`all-docs.adoc`](generated/modulith/all-docs.adoc)。

当前存在 **1 个强连通分量**（3 模块循环）：

```
commerce → course → learning → commerce
（另有 commerce ↔ course 的直接回路）
```

根因：各模块互相消费对方的 `*.api` 契约包——

- `commerce.order.CatalogRepository` 依赖 `course.api.CatalogQuery`（商店展示课程）；
- `course.series.SeriesRepository` / `course.governance.CourseGovernanceService` 依赖 `commerce.api.EntitlementQuery`（权益判断）；
- `course.series.SeriesRepository` 依赖 `learning.api.ProgressQuery`，`learning` 又依赖 `course.api` / `commerce.api`。

这是"共享数据库 + api 契约"式单体的典型形态：包级没有循环，但**模块级有循环**。

### 棘轮策略（本期采用）

- 循环基线：[`docs/generated/modulith-cycle-baseline.txt`](generated/modulith-cycle-baseline.txt)（当前一行：`commerce,course,learning`）；
- 测试 `ModulithModulesTest#moduleCyclesMatchBaseline`：
  - 出现**新**循环 → 构建变红；
  - 消除了循环但未改小基线 → 也变红（迫使基线只降不升，与数据边界门禁同思路）；
- 因此 P4 第一阶段**不重构包结构**也能获得防退化保护。

## 4. 下一阶段（消除循环，二选一）

| 方案 | 做法 | 代价 | 评价 |
|---|---|---|---|
| A. 抽出契约模块 | 把全部 `*.api` 包迁到 `modules.contracts`（按域分子包），业务模块只依赖 contracts | 改 import 多、但机械；契约模块无业务依赖，循环消失 | **推荐**：一次到位，与 Modulith 模型一致 |
| B. 事件化读模型 | 权益/进度改由事件同步到本模块读模型，或由 operations 侧聚合 | 改成异步一致性，改动更大，且初期收益不确定 | 留到真正需要解耦时 |

推荐顺序：A（P4 第二阶段）→ 观察是否还需要 B；A 完成后再把 `@ApplicationModule(allowedDependencies=...)` 逐模块声明，把"允许依赖"也变成编译期契约。

## 5. 与 ArchUnit 的关系

| 工具 | 粒度 | 职责 |
|---|---|---|
| ArchUnit（9 条规则） | 包/类级 | 禁止 platform 反向依赖、payment 边界、operations 不碰实现等**方向性规则** |
| Spring Modulith | 模块级 | 模块依赖图、循环检测（棘轮）、模块文档生成；后续 allowedDependencies |

两者互补：ArchUnit 管"某个包不许指向谁"，Modulith 管"整体图是否有环、依赖是否被声明"。

## 6. 如何刷新模块图

```bash
cd server
mvn -B -Dtest=ModulithModulesTest test        # 生成 target/spring-modulith-docs/
cp target/spring-modulith-docs/*.puml target/spring-modulith-docs/all-docs.adoc ../docs/generated/modulith/
```

CI 中 `mvn test` 会自动执行模块验证；新增循环会让 backend job 变红。
