# 模块化内核与 P4 实施记录（第一阶段：Spring Modulith 接入）

> 日期：2026-11-18　范围：P4（模块化内核）——第一阶段接入门禁 + 第二阶段抽取契约模块消除循环
> 结论：Spring Modulith 2.1.2 已接入；`*.api` 契约已抽成独立 `contracts` 模块，
> 模块图**无循环**、循环基线已删除、`modules.verify()` 硬门禁全绿；模块图文档自动生成。

## 1. 为什么用 Modulith

- 现有 9 条 ArchUnit 规则是**包级**约束（例如 payment 不得依赖 order），但回答不了"模块之间有没有循环、谁依赖谁"；
- Spring Modulith 以"模块依赖图"为一等公民：能检测循环、生成模块文档、后续可做事件发布/模块级 allowedDependencies；
- 2.1.2 对齐 Spring Boot 4.1（本项目当前底座），`ApplicationModules.of(...)` 只做静态分析，无运行时侵入。

## 2. 模块边界（as-built）

模块 = `com.wherelee.edu.modules` 的直接子包：

| 模块 | 职责 | 直接依赖（当前） |
|---|---|---|
| `contracts` | 跨模块契约：各模块对外接口 + DTO（只依赖 platform） | platform（`Type.OPEN`，契约模块） |
| `platform` | 共享内核：租户、追踪、告警、存储、AOP、通用配置 | 无业务依赖（`Type.OPEN` 共享内核） |
| `identity` | 账号、登录、JWT、邀请、角色权限（RBAC） | platform |
| `course` | 系列/章节/视频、课程治理、教师端内容 | platform, identity, commerce, learning |
| `commerce` | 订单、支付、退款、权益、对账 | platform, course |
| `learning` | 学习空间、进度、播放日志 | platform, course, commerce |
| `operations` | 运营后台（订单/用户/课程/对账/角色管理） | platform, identity, course, commerce, learning |

各模块 `package-info.java` 声明 `@ApplicationModule(displayName, allowedDependencies)`：
`contracts→{platform}`、`platform→{}`、其余业务模块统一 `→{platform,contracts}`。
未声明的跨模块依赖会让 `ModulithModulesTest#moduleBoundariesAreIntact` 变红。

边界规则（ArchUnit 已覆盖部分，Modulith 图为准）：

- `platform` 不得依赖任何业务模块；
- `identity` 只依赖 `platform`；
- `learning` 只能依赖 `course.api` / `commerce.api` 契约，不得依赖实现与 `identity`/`operations`；
- `commerce` 不得依赖 `operations`；`payment` 子包不得依赖 `order`/`entitlement`；
- `operations` 只通过各模块 api / 服务访问，不直接碰存储实现。

## 3. 依赖图与循环（已消除）

P4 第二阶段把 `course.api` / `commerce.api` / `learning.api` / `identity.api` 四个契约包
（含 `OrderDtos` / `PaymentDtos` 等共享 DTO）统一迁到 `modules.contracts`，并顺带修掉两处绕过契约的直连：

- `operations.alert.PaymentAlertJob` 原直接依赖 `commerce.payment.PaymentRepository/PaymentProperties`
  → 改为依赖 `contracts.commerce.PaymentAlertQueries`（实现 `PaymentAlertQueryService`）；
- `operations.admin.RoleAdminController` 原直接依赖 `identity.rbac.RoleAdminService/RbacRepository`
  → 改为依赖 `contracts.identity.RoleAdminOperations`（`RoleAdminService` 实现该契约）。

结果：业务模块之间不再互相依赖，模块图无环，循环基线文件已删除。

## 4. 门禁机制（已生效）

- `ModulithModulesTest#moduleBoundariesAreIntact` 直接调用 `modules.verify()`：
  循环依赖、未声明的跨模块依赖、非暴露类型泄漏任一出现都会让 `mvn test` 与 CI 变红；
- `contracts` 与 `platform` 声明 `Type.OPEN`（契约/共享内核），业务模块仍保持"内部类型不暴露"；
- 循环基线机制已随循环消除一并删除（不再需要棘轮）；
- 模块图与模块文档由 `Documenter` 生成，快照提交在 `docs/generated/modulith/`。

## 5. 与 ArchUnit 的关系

| 工具 | 粒度 | 职责 |
|---|---|---|
| ArchUnit（9 条规则） | 包/类级 | 禁止 platform 反向依赖、payment 边界、operations 不碰实现等**方向性规则** |
| Spring Modulith | 模块级 | 模块依赖图、循环检测（棘轮）、模块文档生成；后续 allowedDependencies |

两者互补：ArchUnit 管"某个包不许指向谁"，Modulith 管"整体图是否有环、依赖是否被声明"。

## 6. 如何刷新模块图

```bash
cd server
mvn -B -Dtest=ModulithModulesTest test        # 生成 target/spring-modulith-docs/
cp target/spring-modulith-docs/*.puml target/spring-modulith-docs/all-docs.adoc ../docs/generated/modulith/
```

CI 中 `mvn test` 会自动执行模块验证；新增循环会让 backend job 变红。

## 8. Maven 多模块（P4-3 进行中）

```
server/
  pom.xml              # 聚合父工程（spring-boot-starter-parent 4.1.2）
  btry-platform/       # 共享内核（platform 包）
  btry-contracts/      # 跨模块契约（依赖 platform）
  btry-app/            # 业务模块 + bootstrap + 启动类 + 资源（依赖 platform/contracts）
```

- 包名未变（`com.wherelee.edu.modules.*`），只拆构建单元；`mvn test` 在 `server/` 下聚合执行；
- 测试容器等价验证：单元 137、集成 39 全绿；数据边界扫描器已适配多模块目录；
- Dockerfile 已改为多模块构建并升级到 Java 21。

### starter 化（已完成）

- `btry-platform` 是真正的 starter：`PlatformAutoConfiguration` + `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，
  自动装配 platform 包内全部内核组件（租户、追踪、告警、存储、AOP、审计、WebConfig）；
- `btry-app` 的 `@SpringBootApplication` 收窄扫描范围（只扫业务模块 + bootstrap），platform 组件全部由 starter 提供，
  彻底验证了"内核可被外部应用直接依赖"；
- 验证：starter 改造后全量单测 137 / 集成 39 全绿（Spring 上下文由 AutoConfiguration 拉起）。

### 模板仓（已完成）

- 仓库：<https://github.com/thereYany/btry-template>
- 内容：`TemplateApplication`（扫描 btry 内核 + 自己的 `com.wherelee.template` 包）、示例垂直业务 Controller（复用内核
  `@RequirePermission` 权限码）、`application.yml`（DB/Redis/JWT/COS 环境变量模板）、README（安装内核 → 启动 → 登录/上传/支付/对账验证步骤）；

## 9. 遗留

1. 模板仓目前依赖本机 `mvn install` 的内核，尚未发布到私有 Maven 仓库；
2. 契约模块目前是 `Type.OPEN`；若未来要把"契约也要显式暴露"收紧，可改为按子包 `@NamedInterface`；
3. 模块内 `internal` 包尚未显式区分（当前依靠"非 api 包即内部"的约定）。
