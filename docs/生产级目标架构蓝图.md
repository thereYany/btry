# btry 生产级目标架构蓝图

更新日期：2026-11-18

状态：**目标态设计（非实施清单）**

本文回答一个问题：**如果按企业生产标准建这套系统，宏观架构长什么样。** 不以"现在规模小"为任何选型依据，也不继承仓内既有文档的保守结论（冲突处见 §13）。

关联：

- `docs/内核与垂直拆分方案.md`（解耦 V2，本文是它的上位架构）
- `docs/生产运维手册.md`（现状运维）
- `docs/Redis降级与MQ边界.md`（本文 §13 明确推翻其中"暂不引入 MQ"的结论）

## 1. 目标态一句话

**多服务 + 每服务独立库 + 托管中间件集群 + 网关统一接入 + 事件驱动跨域一致 + SLO 驱动的可观测与运维**，底座跑在 K8s 上，业务能力（身份/支付/媒体）以独立服务形态供多个项目复用。

不是"把单体切碎"，而是**先把数据切成互不共享的域，再让服务边界跟着数据走**。顺序反了会重构两次。

## 2. 八条架构原则

1. **数据是最高耦合，先分库再分服务**。跨库 join 是架构事故，不是优化项。
2. **同步只走最短路径，跨域状态变更一律事件**。查询可以同步；"钱变了、权限变了"必须异步可靠传播。
3. **不用分布式事务中间件**。用本地事务 + 事务消息/发件箱 + 幂等消费 + 对账，这是支付域的行业共识（2PC/XA 在长事务、渠道回调场景会锁死）。
4. **无状态、幂等、可重放**。服务无本地状态；所有写接口有幂等键；所有消息可重投不产生副作用。
5. **可观测性优先于功能**。没有 SLO、指标、追踪、告警的能力不上线。
6. **多租户从第一天设计**。`tenant_id` / `app_id` 贯穿所有表与接口；后期补是重写。
7. **一切数据变更用 expand-contract**。先加后迁再删，任何迁移不停机、可回滚。
8. **买基础设施，自建业务**。数据库、消息、缓存、对象存储、监控存储用云托管；领域逻辑与一致性方案必须自研。

## 3. 目标全景

```text
                          ┌──────────────┐
 用户 ──► DNS/WAF/CDN ──► │  接入层       │
                          │  APISIX 网关  │  路由 / 统一验签 / 限流 / 灰度 / 埋点
                          └──────┬───────┘
                                 │
        ┌──────────┬─────────────┼─────────────┬──────────┐
        ▼          ▼             ▼             ▼          ▼
   identity-svc payment-svc  order-svc    catalog-svc  media-svc
        │          │             │             │          │
        ▼          ▼             ▼             ▼          ▼
   identity_db payment_db    order_db     catalog_db   media_db
        ▲          ▲             ▲             ▲          ▲
        └──────────┴──── 只通过 API / 事件 ─────┴──────────┘
                                 │
        ┌────────────────────────┼─────────────────────────┐
        ▼                        ▼                         ▼
  learning-svc               ops-svc                 支撑层
        │                        │             Nacos / RocketMQ / Kafka
        ▼                        ▼             Redis Cluster / XXL-Job
   learning_db                ops_db          OTel Collector / Prometheus
                                              Loki / Tempo / Grafana / Alertmanager
                                              KMS / TCR / ArgoCD
```

分层职责：

| 层 | 组件 | 职责 |
|---|---|---|
| 接入层 | 云 WAF + CDN + APISIX 网关 | TLS 终止、JWT 验签、租户识别、全局限流、灰度路由、访问日志 |
| 应用层 | 6–8 个业务服务 | 各自领域逻辑，互相只通过 API/事件 |
| 中间件层 | Nacos、RocketMQ、Kafka、Redis Cluster、XXL-Job | 注册配置、业务消息、数据管道、缓存/会话/锁、调度补偿 |
| 数据层 | 每服务独立 MySQL 实例/库 + COS | 数据所有权，禁止跨库访问 |
| 观测层 | OTel + Prometheus + Loki + Tempo + Grafana + Alertmanager | 指标、日志、追踪、告警、值班 |
| 交付层 | GitLab CI → TCR → ArgoCD → TKE | 镜像化、不可变部署、金丝雀、自动回滚 |

## 4. 中间件选型

选型标准只有三条：**能否支撑资金链路可靠性、能否多云/自托管不锁死、运维是否可自动化**。

| 能力 | 选型 | 理由 | 备选与代价 |
|---|---|---|---|
| 注册与配置 | Nacos 集群（3 节点，按 namespace 隔离环境/项目） | 注册+配置一体，推送快，国内生态成熟 | Eureka+Spring Cloud Config 已停止演进；Consul 运维复杂度更高 |
| 业务消息 | RocketMQ 5.x（NameServer ×2 + Broker 主从，云版优先） | 事务消息、顺序消息、延迟消息、重试+死信，恰好覆盖支付/履约 | Kafka 事务语义弱、延迟消息需额外方案 |
| 数据管道 | Kafka（云版） | 埋点、CDC、日志、数仓入口，吞吐优先 | 用 RocketMQ 兼做会导致业务消息被日志流量挤占 |
| 缓存 | Redis Cluster（3 主 3 从，或云集群版），**按用途隔离实例** | 缓存/会话/限流/分布式锁共用一套会互相拖死 | 单主+哨兵撑不住热点与扩容；Codis 已过时 |
| 数据库 | MySQL 8.0 高可用（云托管或 MGR 三节点）+ 读写代理 | 生态、工具、招人成本最低；MGR 提供自动选主 | 云原生分布式库（TiDB）适合超大规模，但成本与运维曲线陡，暂不引入 |
| 分片 | ShardingSphere-Proxy（分片 + 读写分离 + 加密列） | 与 MySQL 兼容，可后置接入，不改业务 SQL 太多 | 客户端分片侵入业务；云分布式库绑定云 |
| 分布式任务 | XXL-Job / PowerJob 集群 | 对账、补偿、归档必须可追踪、可分片、可重试、可手动触发 | Spring `@Scheduled` 多副本会重复执行，生产不可用 |
| 服务保护 | Sentinel（控制台） | 流控、熔断、热点参数限流、系统自适应保护，规则可动态下发 | Resilience4j 只能代码级配置，无统一控制台 |
| 网关 | APISIX | 动态路由、插件化鉴权/限流、灰度、可观测 | Spring Cloud Gateway 与业务同栈但需自研运维能力 |
| 链路追踪 | OTel Collector + Tempo/Jaeger | 厂商中立，跨服务/跨 MQ 传播 | 各云 APM 均可替代，但会绑定 |
| 指标 | Prometheus + VictoriaMetrics（长期存储） | 生态标准；VM 解决保留期与成本 | 纯 Prometheus 长期存储成本高 |
| 日志 | Loki（或云 CLS/OpenSearch） | 与 Grafana 一体，标签化成本低 | ELK 功能强但资源占用高 |
| 告警 | Alertmanager + 值班（IM/电话） | 分级、抑制、静默、SLO burn rate | 仅靠阈值告警会产生噪音 |
| 密钥 | 云 KMS / Secrets Manager | 密钥不进仓库、不进镜像、可轮换 | 环境变量明文是事故源 |
| 对象存储 | COS（私有桶）+ CDN + 回源鉴权 | 视频/文件不落应用服务器 | 自建 MinIO 可作为本地开发/灾备 |

**双 MQ 不是过度设计**：业务消息要求"可靠、有序、可重试、事务"，日志埋点要求"高吞吐、可丢、可批量"。用一套必然牺牲一头。

## 5. 服务拆分

| 服务 | 领域职责 | 数据库 | 对外接口 | 发布事件 |
|---|---|---|---|---|
| `identity-svc` | 账号、凭证、角色权限、租户与应用注册、SSO 扩展点 | identity_db | 登录/换 token/验签公钥/账号管理 | 账号变更、角色变更 |
| `payment-svc` | 支付单、渠道路由、退款、对账、结算（**通用中台，不认识业务**） | payment_db | 创建支付/查询/退款/回调/对账 | 支付成功/失败/退款完成 |
| `order-svc` | 交易订单、订单状态、履约编排（业务侧） | order_db | 下单/订单查询/关单 | 订单已支付/已履约 |
| `catalog-svc` | 内容目录、结构、定价、促销 | catalog_db | 商品/目录/价格查询与治理 | 内容上下架、价格变更 |
| `media-svc` | 媒体资产元数据、直传凭证、播放签名、CDN 鉴权 | media_db | 上传票据/完成确认/签名 URL | 资产就绪 |
| `learning-svc` | 权益（entitlement）、学习进度、播放行为 | learning_db | 权益校验/进度读写/行为上报 | 权益发放/回收、进度事件 |
| `ops-svc` | 运营后台聚合（BFF）、告警、审计、补偿台 | ops_db | 管理端接口 | — |
| （可选）`notify-svc` | 短信/邮件/站内信/webhook 投递 | notify_db | 发送任务 | 投递结果 |

拆分准则（写进架构评审 checklist）：

1. 一个服务 = 一个可以**独立发版**的业务能力；
2. 一个服务 = **一个数据库**，跨库只能 API/事件；
3. 服务间同步调用超过 2 跳的链路必须重新设计；
4. 两个服务如果总是同时发版，说明边界画错了——合并而不是继续拆；
5. 共享代码只允许是 SDK（可观测、幂等、异常、审计），不允许共享领域模型。

## 6. 数据架构大改

### 6.1 分库

| 库 | 内容 | 保护等级 | 备份策略 |
|---|---|---|---|
| `identity_db` | 账号、凭证、角色权限、租户、应用 | 高 | 每日全备 + binlog，RPO 分钟级 |
| `payment_db` | 支付单、尝试、事件、退款、发件箱、对账 | **最高** | 每日全备 + binlog 实时 + 异地周备；独立实例，不与业务共库；审计开启 |
| `order_db` | 订单、明细、状态流水 | 高 | 每日全备 + binlog |
| `catalog_db` | 目录、结构、价格、促销 | 中 | 每日全备 |
| `media_db` | 媒体资产元数据 | 中 | 每日全备 |
| `learning_db` | 权益、进度、播放行为（大表） | 中 | 每日全备 + 分区归档 |
| `ops_db` | 审计、告警、补偿任务 | 中 | 每日全备 |

硬约束：**每个库独立账号、独立连接池、独立备份**；应用账号无 `DROP`/`ALTER` 权限（DDL 走流水线）；跨库查询在代码评审里一票否决。

### 6.2 多租户模型

三层：`platform`（平台）→ `tenant`（机构/客户）→ `app`（接入的业务系统）。

| 隔离档位 | 适用 | 实现 |
|---|---|---|
| **Pool**（默认） | 绝大多数租户 | 共享库共享表 + `tenant_id`/`app_id` 列 + MyBatis 拦截器强制注入 + 唯一索引含租户 |
| **Bridge** | 中型客户 | 共享实例、独立 schema |
| **Silo** | 大客户/合规要求 | 独立实例，按分发配置部署同镜像 |

落地要点：

- 所有业务表必须有 `tenant_id`，支付/订单/内容表额外有 `app_id`；
- 唯一索引一律带租户前缀（如 `uk_tenant_order_no(tenant_id, order_no)`）；
- 网关解析 token 得到 `tenant_id`，服务禁止信任请求体里的租户字段；
- 缓存 key、消息 tag、日志 MDC 全部带租户维度，否则排障时无法隔离。

### 6.3 关键表模型（宏观）

**支付域**（`payment_db`）

```text
payment_order       支付单：payment_no / app_id / tenant_id / biz_type / biz_no /
                    amount / currency / status / channel / provider_trade_no /
                    notify_url / metadata / expire_at / version
                    唯一键：(app_id, biz_type, biz_no)、(channel, provider_trade_no)
payment_attempt     每次发起渠道的尝试，主键 payment_no + attempt_no
payment_event       渠道回调/查单事件，唯一键 (channel, event_key)，落库即去重
refund              退款单，唯一键 refund_no、幂等键 (payment_no, client_refund_id)
payment_outbox      事务性发件箱：与状态变更同事务写入，独立线程投递
recon_task          对账任务：渠道 / 账期 / 状态 / 差异数
recon_diff          差异明细：类型 / 期望 / 实际 / 处理人 / 处理结果
channel_bill        渠道账单原始数据（对象存储 + 索引）
settlement          结算/清分明细
```

**订单域**：`order` / `order_item` / `order_ext`（业务自定义字段）/ `order_status_log`（状态流水，审计与排障用）。

**内容域**：`catalog_item` / `catalog_structure`（章节树：邻接表 + 物化路径，避免递归查询）/ `price` / `promotion` / `promotion_rule`。

**媒体域**：`media_asset`（object_key / size / mime / checksum / status / owner_type / owner_id），与"课程"解耦。

**学习域**：`entitlement`（主体 / 资源类型 / 资源 ID / 有效期 / 来源）/ `entitlement_log` / `progress` / `playback_event`（大表，按月分区）。

**身份域**：`account` / `credential` / `role` / `permission` / `account_role` / `role_permission` / `tenant` / `app` / `api_key`。

**运营域**：`audit_log`（谁在什么时候对什么做了什么，不可变）/ `alert` / `compensation_task`。

### 6.4 ID、状态与金额

- 内部主键：雪花 ID（`BIGINT`），保证分库后不冲突；
- 外部单号：`前缀 + yyyyMMdd + 分片号 + 序列`（支付/订单/退款各自前缀），可读、可追、不可猜；
- 状态：枚举 + 条件更新（`WHERE status = ? AND version = ?`）+ **状态流水表**；
- 金额统一 `BIGINT` 分，禁止浮点；币种单独列；
- 时间统一 `DATETIME(3)` 且按 UTC 存储，展示层转换；
- 所有表带 `created_at` / `updated_at`，软删用 `deleted_at`，禁止物理删（支付/订单永久保留）。

### 6.5 分区与分片

**先分区，后分片**：

| 表 | 策略 |
|---|---|
| `playback_event` | 按月 RANGE 分区，热 30 天，超期分区导出后 drop |
| `audit_log` | 按月分区，保留 6–12 个月 |
| `order` / `payment_order` | 按年分区；单表超 5000 万或写入超单库 30% 再分片 |
| `recon_diff` | 按账期分区 |

分片触发条件（写死，不拍脑袋）：单表 > 5000 万行、单库写入 QPS > 3000、单库磁盘 > 1TB。分片键：订单/权益按 `user_id`，支付按 `app_id`，避免跨分片事务。

### 6.6 读写分离与一致性

- 主库写、从库读，代理层（ShardingSphere-Proxy）做路由；
- **强一致读走主库**：支付状态、订单状态、权益校验等"钱与权限"的读，代码上强制主库（注解或 Hint），不能靠"从库应该同步完了"；
- 从库延迟指标必须暴露（`mysql_slave_seconds_behind_master`），超阈值自动把读切主并告警；
- 写后立即读的场景用"同事务内读主库"，不要依赖缓存。

### 6.7 CDC 数据管道

`Canal/Debezium → Kafka → 下游`，三条用途：

1. **缓存失效**：数据变更发失效消息，替代"删缓存双写"的不确定性；
2. **搜索/报表**：运营检索与统计走独立存储，不拖生产库；
3. **风控/审计**：资金表变更留痕，异常模式实时告警。

### 6.8 冷热与归档

- 热：MySQL（最近 30–90 天）；
- 温：分区表或归档库（按月导出，仍可查）；
- 冷：COS 上的 Parquet/JSON 归档（3 年以上，成本最低）；
- 支付/订单凭证类数据不删，只归档；日志/埋点按合规要求（建议 6 个月）到期删除。

### 6.9 数据库高可用与备份

| 项 | 目标 |
|---|---|
| 部署 | 同城双可用区主从（半同步复制）；MGR 或云高可用版自动选主 |
| RPO | 支付库 0（半同步 + 事务消息），其他库 ≤ 5 分钟 |
| RTO | 主从切换 ≤ 5 分钟（自动）；机房级 ≤ 30 分钟（需演练） |
| 备份 | 每日全备 + binlog 持续；每周异地（跨 region）备份 |
| 演练 | **每季度做一次真实恢复演练**，只备份不恢复等于没备份 |
| DDL | 一律 gh-ost / pt-osc 在线变更，禁止业务高峰 DDL，禁止长事务 |

### 6.10 迁移策略

所有表结构变更走 expand-contract 三段：

1. **Expand**：加新列/新表，双写，读旧；
2. **Migrate**：回填历史数据（分批），双读比对，差异归零；
3. **Contract**：切读新结构，观察一个完整业务周期，再删旧列。

禁止：一次性大表重建、停机迁移、在业务代码里做数据修补。

## 7. 关键链路

### 7.1 支付链路（全系统最高标准）

```text
1  order-svc   创建订单（本地事务，状态 CREATED）
2  order-svc   调 payment-svc 创建支付单（幂等键 app_id+biz_type+biz_no，重复则返回原单）
3  payment-svc 本地事务：写 payment_order + payment_outbox
4  返回收银台地址（渠道下单），用户支付
5  渠道回调 → 网关（验签前放行白名单 + 限流）→ payment-svc
6  payment-svc 验签 → payment_event 唯一键去重 → 金额校验 → 状态机
               → 本地事务：payment_order 状态 + payment_outbox
7  outbox dispatcher → RocketMQ 事务消息 → 各订阅方
8  order-svc   幂等消费（消费幂等表 + 唯一键）→ 订单 PAID → 发 OrderPaid
9  learning-svc 消费 OrderPaid → 发放权益（幂等）
10 失败：重试（指数退避）→ 死信 → 补偿任务 → 人工台
11 兜底：主动查单（分钟级）+ T+1 全量对账 + 准实时差异检测
```

铁律：

- **回调只改支付库，绝不改业务库**；
- **不在回调里发 MQ**（双写必出事），一律 outbox；
- **对账是最后防线**，任何"通知成功"都不等于"账平了"；
- 金额不一致 → 挂起 + 告警 + 人工处理，**不自动发货**；
- 幂等键三层：接口幂等（client_request_id）、业务唯一键（biz_no）、事件唯一键（event_key）。

对账体系三件套：

| 层 | 频率 | 作用 |
|---|---|---|
| 实时补偿 | 分钟级 | 主动查单、超时关单、PAID 未履约补发 |
| 准实时差异 | 5–15 分钟 | 我方成功/渠道无单、渠道成功/我方无单 |
| T+1 全量 | 每日 | 渠道账单逐笔比对，差异入 `recon_diff`，人工处理台闭环 |

### 7.2 媒体链路

```text
教师端 → media-svc 申请直传票据（预签名 PUT，限大小/类型/路径前缀，短 TTL）
       → 前端直传 COS（分片上传，断点续传）
       → media-svc 完成确认（回查 objectMetadata 校验大小/类型，落 media_asset READY）
学员端 → learning-svc 校验权益（本地库）→ media-svc 签发 CDN 签名 URL（短 TTL）
       → CDN 边缘 → 回源 COS（私有桶 + 回源鉴权）
       → 播放器按需续签，不泄露源站
行为   → 前端埋点 → 网关 → Kafka → 数仓/学习域聚合
```

要点：

- 播放 URL **短 TTL（5–15 分钟）+ CDN 鉴权 + referer 白名单**，长 TTL 缓存是"链接即凭证"的隐患；
- 上传必须服务端限制体积（预签名策略里的 `content-length-range`），不能信客户端；
- 大文件**分片 + 断点续传**，4GB 单次 PUT 在移动网络必失败；
- 媒体元数据与"课程"解耦（`media_asset.owner_type/owner_id`），换项目直接复用；
- 下架/过期必须**实时生效**：签发前校验内容状态，且缓存 key 带状态版本。

### 7.3 身份与网关

- 网关统一验签（JWT RS256，公钥从 identity-svc/配置中心拿），服务只信任网关注入的内部 header + mTLS；
- Token：access 30 分钟 + refresh 7 天（可吊销，Redis 存版本号）；
- 强制下线：`token_version` 自增 + 网关校验，禁用账号立即生效；
- 授权：RBAC 起步（角色-权限码），预留 ABAC 扩展点（资源属性 + 环境条件）；
- 密钥：签名密钥托管 KMS，支持双密钥轮换（kid）。

## 8. 高可用体系

### 8.1 SLO 与错误预算

| 指标 | 目标 | 说明 |
|---|---|---|
| 核心 API 可用性 | 99.95% | 支付/登录/下单/播放签发 |
| 支付成功率 | ≥ 99.9%（剔除渠道侧失败） | 我方原因导致的失败必须 < 0.1% |
| 支付确认时延 P99 | < 3s | 回调到订单 PAID |
| 对账差异率 | < 0.01% | 超阈值冻结发布 |
| 履约滞后 | P99 < 60s | PAID → 权益可用 |

发布节奏由错误预算决定：预算耗尽则冻结功能发布，只允许修复。

### 8.2 服务高可用

- 每服务 ≥ 2 副本，跨可用区，Pod 反亲和；
- 无状态 + 会话/缓存外置；
- 优雅停机：`preStop` 摘流量 → 等待在途请求 → 进程退出；
- HPA：CPU + 自定义指标（QPS、队列积压）；
- PDB：保证滚动期间可用副本数；
- 依赖隔离：每个外部依赖独立线程池/信号量 + 超时预算 + 熔断 + 降级路径。

### 8.3 发布与变更

- 不可变镜像 + GitOps（ArgoCD），禁止手工改生产；
- 金丝雀：5% → 25% → 100%，按错误率/延迟自动回滚；
- 数据库变更与代码变更解耦（expand-contract），先兼容后切换；
- 功能开关（feature flag）管理灰度和紧急关停；
- 变更窗口 + 回滚预案 + 变更后观察期（至少 30 分钟关键指标）。

### 8.4 容灾

| 级别 | 目标 | 手段 |
|---|---|---|
| 单实例故障 | 无感 | 多副本 + 健康检查 |
| 单可用区故障 | 分钟级 | 跨 AZ 部署 + DB 主从自动切换 |
| 单地域故障 | 30 分钟内 | 异地备份 + 冷备环境 + 预案演练 |
| 依赖故障（MQ/Redis） | 降级可用 | 本地兜底/队列落库/只读降级 |

每季度至少一次混沌演练：杀 Pod、切 DB 主从、断 Redis、MQ 消费延迟、AZ 网络隔离。

### 8.5 容量与成本

- 压测基线（k6 已有）→ 得出单副本容量 → 按 60% 水位扩容；
- 关键指标：QPS、P99、连接池、GC、队列积压、DB 慢查询；
- 容量评审纳入发布流程（大促/活动前）。

## 10. 安全与合规

## 11. 平台化：多项目复用

两条腿走路：

1. **能力服务化**：`identity-svc`、`payment-svc`、`media-svc` 作为独立服务，按 `app_id` 接入多个业务系统；
2. **工程能力 SDK 化**：`kit-starter`（web / 可观测 / 审计 / 幂等 / 限流 / 异常规范）打成依赖，新服务引入即得，不需要重复实现。

新项目接入流程（目标：1 天内跑通）：

```text
1 在 identity-svc 注册 tenant/app，拿到 app_id + client 凭证
2 网关加一条路由 + 限流策略
3 新服务引入 kit-starter，配好 Nacos namespace 与数据源
4 需要支付：接 payment-svc 的 CreatePayment（一个 SDK 方法）
5 需要媒体：接 media-svc 的直传票据 + 签名 URL
6 自己的业务表 + 自己的领域逻辑（唯一需要写的东西）
```

隔离策略：默认 Pool 模式共享服务；大客户/合规要求走 Silo（独立实例，同镜像不同配置）。**禁止代码分叉**。

## 12. 成本与"买 vs 建"

| 项 | 建议 | 理由 |
|---|---|---|
| MySQL | 买云高可用版 | 主从切换、备份、监控、慢日志是长期运维负担 |
| Redis | 买云集群版 | 扩容与故障转移自己搞性价比极低 |
| RocketMQ / Kafka | 买云版（或先单集群托管） | 消息中间件的可靠性维护成本高 |
| 对象存储 + CDN | 买 | 无自建理由 |
| 可观测存储 | 买或半托管（Prometheus 自建 + 对象存储长期） | 日志/指标存储增长快 |
| K8s | 买托管（TKE）或自建 K3s | 托管省 control plane 运维 |
| 业务服务 | 自建 | 这是你的核心竞争力 |

量级估算（入门生产级）：6–8 个服务 × 2 副本（小规格）+ 云 DB（主从）+ 云 Redis + 云 MQ + 可观测，月成本约数千元级别；**具体数字取决于规格与保留期，落地前用云厂商计算器实测**。自建可压到一半，但运维人力成本会补回去。

单人维护这套的唯一可行方式是：**托管中间件 + 全自动流水线 + 只对 SLO 负责的告警**，不追求"什么都自己运维"。

## 13. 与现有文档的冲突（明确推翻）

| 旧结论 | 位置 | 本文结论 | 理由 |
|---|---|---|---|
| 暂不引入 MQ | `Redis降级与MQ边界.md` §6 | **引入 RocketMQ**，用于支付事件与跨域状态传播 | 跨服务一致性必须依赖可靠消息；"事务 + 补偿任务"只在单体能成立 |
| 资金链路保持同步事务 | `模块解耦设计计划.md` §6 | **本地事务 + 事务消息 + 幂等 + 对账** | 服务拆分后不存在跨库事务；对账才是资金正确性的最终保障 |
| 暂不引入事务性 outbox | `模块解耦实施清单.md` | **outbox 是标配** | 双写（DB+MQ）在崩溃点必丢消息，outbox 是唯一可靠解法 |
| 当前系统单实例 | `Redis降级与MQ边界.md` | **无状态多副本 + 会话外置** | 单实例是可用性单点，与 SLO 目标冲突 |
| 播放 URL 缓存 210 分钟 | `application.yml` / 视频方案 | **短 TTL + CDN 鉴权** | 长 TTL 缓存 + 无绑定等于链接即凭证 |
| Spring `@Scheduled` 跑对账/补偿 | 现状代码 | **XXL-Job 集群调度** | 多副本下会重复执行，且不可手动触发/不可观测 |

**保留的旧结论**：ArchUnit 模块边界测试、端口/适配器分层、Redis 不作为资金正确性来源、DB 是事实来源——这些方向正确。

## 15. 明确不做

| 不做 | 理由 |
|---|---|
| Seata AT / XA 全局事务 | 与长事务、渠道回调冲突，故障时全局阻塞 |
| 自研数据库/消息中间件 | 无收益，纯风险 |
| 一开始就 10+ 微服务 | 服务粒度按"独立发版能力"定，不是按"看起来解耦"定 |
| 每个服务独立 K8s 集群 | 运维爆炸，逻辑隔离即可 |
| 大而全的中台概念 | 只平台化真正被第二个项目复用的能力（身份/支付/媒体/工程 SDK） |
| 无 SLO 的"高可用" | 无法验证的高可用是口号 |
