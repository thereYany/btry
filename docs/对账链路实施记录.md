# 对账链路实施记录（P2-R）

更新日期：2026-11-18

状态：**链路已跑通，5 个集成用例全绿**

## 1. 为什么先做对账

支付单独立（P1）之后，系统里存在两个"事实来源"：我方的支付单状态、渠道回给我们的状态。两者必须能持续对得上，否则"支付成功"只是一次网络调用成功。对账是资金正确性的最后防线，也是后续把履约改成事件驱动的安全网——事件丢了、重复了、顺序错了，对账都能兜住。

## 2. 设计

```text
渠道账单（ChannelBillProvider 端口）
        │  MOCK：支付尝试表里渠道回报的结果
        │  支付宝/微信：账单文件解析 / 账单接口拉取（后续 adapter）
        ▼
ReconciliationService
        │  我方：t_payment_order（channel + paid_at 当天，状态 PAID）
        │  按 provider_trade_no 逐笔匹配
        ▼
t_recon_task（一次对账 = 一个任务）+ t_recon_diff（差异明细）
        │
        ▼
运营端对账台：查看差异 → HANDLED / IGNORED
```

关键接口：

| 类型 | 位置 | 说明 |
|---|---|---|
| `ChannelBillProvider` | `commerce/payment/recon` | 账单数据源端口，新增渠道只需实现它 |
| `MockChannelBillProvider` | 同上 | Mock 渠道：用支付尝试里的渠道回报构造账单 |
| `ReconciliationService` | 同上 | 比对、落差异、任务统计、人工处理 |
| `AdminReconciliationOperations` | `commerce/api` | 运营端契约（operations 只依赖它） |
| `AdminReconciliationController` | `operations/admin` | 触发对账 / 查差异 / 处理差异 |
| `ReconciliationJob` | `commerce/payment/recon` | 每日 03:30 自动对昨日账单 |

## 3. 四类差异

| 类型 | 含义 | 处理原则 |
|---|---|---|
| `LOCAL_ONLY` | 我方已支付，渠道账单没有（或缺少渠道流水号） | 不可自动补偿，人工核对渠道后台 |
| `PROVIDER_ONLY` | 渠道有单，我方没有 | 最高危：可能漏发权益，优先处理 |
| `AMOUNT` | 金额不一致 | 金额不符必须人工，绝不自动发货 |
| `STATUS` | 我方成功、渠道失败（或反之） | 人工核对后决定是否回滚/补发 |

差异只入库、**不自动改单**。原因很简单：对账算法也有 bug 的可能，用有 bug 的算法去自动改钱，是把风险放大。

## 4. 幂等与可重跑

- 任务号 = `RECON-{channel}-{billDate}`，唯一键 `(channel, bill_date)`；
- 重跑复用任务号、清空旧差异后重算，不会产生重复差异；
- 账单登记表 `t_channel_bill` 存 checksum 与行数，便于发现"账单文件变了"；
- 单次对账在一个事务内完成（任务 + 差异 + 统计）。

## 5. 接口

```http
POST /api/admin/recon/run?channel=MOCK&billDate=2026-11-17
     → { taskNo, totalCount, matchedCount, diffCount, diffByType }

GET  /api/admin/recon/diffs?status=OPEN&page=1&size=20
     → PageResult<DiffView>

PUT  /api/admin/recon/diffs/{id}/handle  { "status": "HANDLED" }
     → 204；重复处理返回 400
```

管理端操作走 `@RequireRole("ADMIN")` + `@AdminAudit`（`RECON_HANDLE`），限流 10 次/分钟、幂等 5 秒。

## 6. 验证证据

`ReconciliationIntegrationTest`（5 个用例）：

| 用例 | 断言 |
|---|---|
| 一致零差异 | total=1 / matched=1 / diff=0；重跑任务号不变、差异不重复 |
| 我方有单渠道无单 | `LOCAL_ONLY` 1 条，paymentNo 正确 |
| 渠道有单我方无单 | `PROVIDER_ONLY` 1 条 |
| 金额 / 状态不一致 | 分别归入 `AMOUNT`、`STATUS`，不同时重复计数 |
| 人工处理闭环 | OPEN→HANDLED 后 OPEN 归零、HANDLED 可查；重复处理与非法状态被拒 |

配套全量结果：

- 单元测试 124 通过；
- 集成测试 **20 通过**（原 15 + 对账 5）；
- 数据边界门禁通过（跨模块表 8 个未增加）。

## 7. 已知限制与下一步

1. **账单源只有 MOCK**：支付宝/微信 adapter 未接，需要真实商户号才能联调；端口已就位，接入不改对账核心。
2. **只对"已支付"**：退款对账（渠道退款单 vs 我方退款单）未纳入，属于 P2 后续。
3. **差异处理无备注/附件**：目前只有状态与处理人，真实财务场景需要备注与凭证。
4. **未做准实时对账**：当前只有 T+1 全量；后续加 5–15 分钟窗口的差异扫描。
