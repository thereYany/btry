# 支付单独立化：影子阶段实施记录（P1）

更新日期：2026-11-18

状态：**影子写 + 双读比对已跑通，读路径未切换**

## 1. 目标与边界

A 期的第一刀：把「支付」从订单的附属表升级为独立聚合，让支付单只认 `app_id + biz_type + biz_no`，不认课程、不认订单表结构。

本阶段**只做加法**：

- 新增支付单、发件箱、对账三组表；
- 订单/支付尝试/事件/退款补 `payment_no` 引用；
- 支付单由订单事实同步而来（影子写），**所有读路径仍走旧模型**；
- 用双读比对持续证明两边一致。

不做：切换读、删除旧列、事件驱动履约、outbox 投递。这些在 P2/P3 做，届时才有回退成本问题。

## 2. 数据模型

### 2.1 新增表

| 表 | 作用 | 关键约束 |
|---|---|---|
| `t_payment_order` | 支付单（独立聚合） | `uk_payment_no`、`uk_payment_biz(app_id,biz_type,biz_no)`、`uk_payment_provider_trade(channel,provider_trade_no)` |
| `t_payment_outbox` | 事务性发件箱（P2 启用投递） | `idx_outbox_due(status,next_at)` |
| `t_recon_task` | 对账任务 | `uk_recon_channel_date(channel,bill_date)` |
| `t_recon_diff` | 对账差异明细 | `idx_diff_status(status,created_at)` |
| `t_channel_bill` | 渠道账单原始记录 | `uk_bill_channel_date(channel,bill_date)` |

### 2.2 引用列

`t_payment_attempt` / `t_payment_event` / `t_refund` / `t_order` 各增 `payment_no`（可空 + 索引），由影子写回填。影子期规则固定为：

```
payment_no = "P" + order_no
```

确定性生成保证重复同步幂等；正式切换时改为序列/雪花并做一次性迁移。

### 2.3 状态映射

支付单只表达「钱」，订单履约完成仍然是 `PAID`：

| 订单状态 | 支付单状态 |
|---|---|
| CREATED | CREATED |
| PAYING | PAYING |
| PAY_FAILED | FAILED |
| PAID / FULFILLED | PAID |
| REFUNDING / REFUNDED / REFUND_FAILED | 同名 |
| CLOSED | CLOSED |

映射集中在 `PaymentStatusMapping`，是单向显式表，不做"看起来差不多"的推断。

## 3. 代码结构

```text
commerce/payment/shadow/
├── PaymentShadowPort          # 业务侧唯一依赖的端口（函数式接口 + NOOP）
├── PaymentShadowRecorder      # 事务提交后触发（afterCommit），失败只告警不阻断
├── PaymentOrderShadowService  # 从订单事实同步支付单 + 双读比对
├── PaymentOrderShadowRepository # 幂等 upsert、引用回填、比对查询
├── PaymentOrderShadowRow      # 支付单行（无任何 course/order 语义）
├── PaymentStatusMapping       # 订单状态 → 支付单状态
├── PaymentShadowNo            # payment_no 生成规则
└── PaymentShadowAuditJob      # 定时比对巡检 + 指标 payment.shadow.differences
```

业务侧只加一行调用（`shadowPort.recordAfterCommit(orderNo)`），分布在 5 个状态变化点：

| 服务 | 触发点 |
|---|---|
| `OrderService` | 创建订单、用户关单 |
| `PaymentService` | 发起支付、过期关单补偿 |
| `PaymentConfirmationService` | 支付事件确认（成功/失败/重复） |
| `OrderFulfillmentService` | 履约成功 |
| `RefundService` | 退款流程结束 |

## 4. 一致性保证

| 机制 | 做法 | 为什么 |
|---|---|---|
| 不阻断资金链路 | `afterCommit` 触发 + 异常吞掉并告警 | 影子表是新增试验模型，写失败不能导致真实支付失败 |
| 幂等 | `payment_no` 确定性 + `ON DUPLICATE KEY` | 重复同步结果一致 |
| 单调（防回退） | `source_updated_at` 守卫列，迟到的旧快照整行不生效 | 并发/重试下状态回退是最容易出的线上事故 |
| 可比对 | 比对口径与同步口径完全一致（订单字段优先、最新尝试兜底） | 否则比对会因"取值来源不同"产生假差异 |
| 可观测 | 指标 `payment.shadow.differences` + 定时日志 | 差异主动浮出，不靠人查 |

`source_updated_at` 的实现细节有坑：MySQL 的 `ON DUPLICATE KEY UPDATE` 按从左到右求值，守卫列必须**最后**赋值，否则后续 `IF` 判断会读到新值、守卫失效。仓库层已有注释。

### 4.3 影子写踩坑：不要碰资金链路的强事务表（2026-11-18 实测）

影子写最初每笔状态变化都会执行 `UPDATE t_order SET payment_no = ? WHERE order_no = ? AND payment_no IS NULL` 来回填引用。上线到测试环境后，`RefundConcurrencyIntegrationTest`（10 线程并发退款）开始稳定失败：

- 2 个线程拿到 `当前订单状态不能退款`；
- 1 个线程在 `UPDATE t_refund SET status='SUCCEEDED'` 上撞 MySQL 死锁。

原因：影子写虽然"通常 0 行受影响"，但 InnoDB 的行/索引锁仍会参与竞争，给 `t_order` 增加了额外的写压力，把并发退款之间的窗口放大。

修法两步：

1. **订单 `payment_no` 在下单时写入**（`OrderRepository.insert` 直接带上），影子写不再更新 `t_order`；
2. 顺手把退款入口做成真正幂等：先查已有退款单再校验订单状态；并发改状态时捕获异常并返回已存在的退款单；对 MySQL 死锁做有界重试（最多 2 次，20/40ms 退避）。

结果：并发退款测试稳定通过，且退款语义更正确（重复退款请求返回同一张退款单，不再报"当前订单状态不能退款"）。

**结论**：影子/旁路写入必须严格限制在**自己拥有的表**上；一旦写入资金主链路的表，就等于在热路径上加锁。
