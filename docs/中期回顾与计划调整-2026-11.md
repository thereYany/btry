# 中期回顾与计划调整（2026-11-18）

> 背景：A 期（数据地基）与 P2（支付反转）已完成。本文件用于中期盘点、在线调研补充、以及对后续路线（P3/P4/P5/平台化）的修订。修订后以本文件为准，旧文档中冲突处见第 6 节。

## 0. 结论先行

1. **现状比预期扎实，但底座已过 EOL**：代码 216 文件 / 12.4k 行、19 张表、58 个接口、52 个测试类（单元 131 + 集成 37 全绿）、9 条 ArchUnit 规则、数据边界门禁 0 跨模块表。但 Spring Boot 3.3.5 的 OSS 支持已于 **2025-06-30 结束**（当前稳定版 4.1.2，OSS 支持至 2027-07-31），作为"生产级"叙事必须先升级底座。
2. **P4 改变实现方式**：不再自研 Maven 多模块 + starter + 模板仓三件套，改用 **Spring Modulith** 做模块边界验证与内部事件，多模块/starter 推迟到"第二个消费者出现"时再做。理由：Modulith 2.1 已是 Boot 4.1 官方对齐方案，`ApplicationModules.verify()` 能把边界规则变成 CI 门禁；提前拆 Maven 模块只会增加构建成本，不产生面试价值。
3. **P5 缩小范围**：**不拆订单/支付/退款**（共享本地事务，拆出去就丢 ACID，需要 Saga + 对账兜底，收益为负）。服务化只针对**异步/读侧**：通知、对账报表、媒体处理。K8s/平台化推迟到有真实多实例/发布需求时；高可用先用"单体多副本 + 探针 + MySQL 主从 + 演练"讲清楚。
4. **不变的部分**：P3 身份通用化仍排第一（无外部依赖、面试高频）；outbox 保留（调研确认它是可靠消息的正确底座，MQ 只负责投递）；真实支付接入仍受商户资质外部依赖，放在 P3/P4 之后。
5. **新增可选加分项**：权限感知 RAG（租户 + 已购权益过滤 + 小评估集），符合当前 Java×AI 招聘趋势，但必须窄而深，不动主线。

## 2. 在线调研结论（截至 2026-11-18）

### 2.1 框架与生态（官方事实为主）

- **Spring Boot**：当前稳定 **4.1.2**（2026-10-22）；4.0 OSS 支持 2026-12-31 结束；3.5 OSS 已结束（2026-06-30）；3.3 OSS 已结束（2025-06-30）。Boot 4.1 支持 Java 17–26。来源：<https://endoflife.date/spring-boot>、<https://spring.io/blog/2025/11/20/spring-boot-4-0-0-available-now>
- **JDK**：Java 25 为最新 LTS（2025-09-16 GA）；Java 21 为上一 LTS。Java 17 的 Oracle premier 支持 2026-09-30 结束。建议 17 → **21**（稳妥、库兼容性好），25 作为可选项。
- **Spring Modulith**：最新 GA **2.1.2**（2026-10-23），2.x 对齐 Boot 4.x；1.x 已 EOL。官方提供 `ApplicationModules.verify()`、事件注册表（同事务写事件表，支持 JPA/JDBC/Mongo/Neo4j）与 staleness 监控。官方文档同时承认内建 externalization 仍缺真正 outbox 的关键特性，2.1 起可接第三方投递。来源：<https://docs.spring.io/spring-modulith/reference/events.html>、<https://spring.io/blog/2026/10/23/spring-modulith-2-2-rc1-2-1-2-2-0-9-and-1-4-14-released>
- **模块化单体 vs 微服务**：主流结论仍是 MonolithFirst——先做边界清晰的单体，达到规模再拆（Thoughtworks 雷达、Martin Fowler）。来源：<https://martinfowler.com/bliki/MonolithFirst.html>
- **可靠消息方案对比**：① 自研 outbox（当前采用，最灵活）；② Debezium Outbox Router（CDC，需要 Kafka Connect + binlog）；③ RocketMQ 事务消息（半消息 + 回查，绑定 RocketMQ）。单库阶段自研 outbox 足够，跨进程再考虑后两者。

### 2.2 支付与多租户

- **支付宝**：OpenAPI v2 与 v3 并存（v3 为 OAS3/RESTful/整报文验签，官方有 `alipay-sdk-java-v3`）。回调重试 8 次/25h，`notify_id` 不变，必须验签 + 校验 `app_id/seller_id/金额`，再按事件去重。账单接口 `alipay.data.dataservice.bill.downloadurl.query`，日账单 T+1 生成。来源：<https://opendocs.alipay.com/open/064jhr>、<https://opendocs.alipay.com/open/203/105286>
- **微信支付**：以 APIv3 为主（JSON + 签名 + AES-GCM），v2 已停止维护；账单次日生成，下载链接短时效且需校验 hash。服务商模式用 `sp_mchid/sub_mchid`。
- **支付生产共识**：幂等键 = 业务单号 + 唯一索引；支付单/尝试/回调/退款四层状态机单向推进；T+1 全量 diff，长短款先挂账隔离再冲正；"回调 + 主动查单"双通道；退款与履约用本地事务 + outbox（跨服务才上 Saga）。
- **MQ 选型**：支付可靠消息选 **RocketMQ 5.x**（事务消息 + 定时消息，适合查单/对账补偿）；Kafka 4.x（仅 KRaft）的事务只覆盖 Kafka 内部 topic+offset，适合流处理，不适合支付可靠消息。**结论：暂不引入 Kafka**。
- **多租户**：Pool 模式（`tenant_id`）仍是默认；MyBatis 插件（如 MyBatis-Plus `TenantLineInnerInterceptor`）能自动拼条件，但要注意异步任务丢上下文、回调无租户需反查、自定义 SQL 绕过等问题；MySQL 无原生 RLS。分库分表（ShardingSphere）解决分片，不解决租户语义。
- **拆服务判断清单**（满足 ≥4 条再拆）：独立发布节奏/团队、跨域事务已 outbox 化、独立扩容需求、单库写入/表规模瓶颈、独立密钥安全域、具备幂等/补偿/可观测运维能力。当前项目仅满足 1–2 条。

### 2.3 求职视角

- 2026 年 Java 后端面试仍是"八股筛人 + 项目分层"：JVM/并发/MySQL/Redis/Spring 是 P0；DDD/分布式事务/消息/可观测性作为微服务追问链的一部分；云原生从加分变标配；AI 从加分变基线认知。
- 个人项目的架构改造，面试官先看真实性，再看取舍：真实规模、指标来源、故障复盘、回退点、ADR 式记录最能加分；堆微服务名词、无来源指标、低流量硬拆是减分项。
- AI 方向值得作为差异化，但要"窄而深"：权限感知的 RAG（租户 + 权益过滤）、评估集、兜底与成本，比一个聊天框可信得多。

## 3. 计划调整对照

| 原计划（拆分方案 §7 / 蓝图 §14） | 调整后 | 理由 |
|---|---|---|
| P3 身份通用化（3–5 天） | **保持第一优先**，但优先用 Spring Security 方法级安全 + 权限表，不新造注解 | 升级到 Boot 4 后 Security 7 能力即可覆盖；少自研 |
| P4 内核抽取：Maven 多模块 + starter + BOM + 模板仓（1–2 周） | **改为：Spring Modulith 模块边界 + ArchUnit 门禁；多模块/starter 只在出现第二个消费者后做；模板仓最后** | Modulith 是官方方案，成本低、CI 可验证；提前拆模块不产生收益 |
| P5 抽 payment 微服务（1–2 周） | **取消**。只抽异步/读侧：通知、对账报表、媒体处理；订单+支付+退款保留同一事务边界 | 支付/订单/退款共享本地事务，拆出即失去 ACID，需 Saga + 对账，收益为负；判断清单不满足 |
| C 平台化：K8s + GitOps + 金丝雀（2–3 周） | **推迟**，门槛：有真实多实例/独立发布需求，或面试明确要求云原生实战 | 单机 systemd 下 K8s 是成本不是收益；本地 kind 实验不计入生产叙事 |
| D 高可用：跨 AZ + DB 自动切换 | **降级为**：单体多副本 + 探针 + MySQL 主从 + 季度演练 + SLO 看板 | 单库单应用先做可验证的恢复能力，跨 AZ 等有真实 SLA 再做 |
| 引入 RocketMQ | **保持候选，暂不引入**；触发条件：跨进程消费/削峰/密集定时任务 | outbox 已解决可靠投递；MQ 是投递通道而已 |
| 真实支付宝接入（v2 SDK） | **升级为 v3 方案**；账单对账按官方 T+1 接口重做 | v3 是官方主推；账单接口才是 T+1 对账的真实数据源 |
| —— | **新增 P0.5 底座升级**：Boot 3.3.5 → 4.1.2、Java 17 → 21 | 3.3 已过 EOL；先升级再改身份/模块，避免二次迁移 |

## 5. 风险与回退

- **Boot 4 升级**：Spring Security 7 DSL、Actuator、Flyway、MyBatis、Resilience4j 都可能破坏兼容。回退：先打 tag，独立分支升级，逐项修复；失败可整体回退到 3.3.5。
- **Modulith 与自研 outbox 重叠**：明确边界——Modulith 只负责"模块边界验证 + 模块内事件分发"，**不接管**支付 outbox 的投递与重试；支付 outbox 保持自研。
- **P5 未来若真要拆支付**：先满足第 2.2 节 6 条判断清单，且把跨域事务全部改为 outbox + 对账兜底后再动。
- **第二垂直域**：必须用真实业务验证，否则视为纸上谈兵（面试减分）。
