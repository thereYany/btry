# P2 支付反转实施记录

> 日期：2026-11-18　范围：P2「支付反转」（A 期支付单独立化的收口）
> 结论：支付域不再依赖订单/权益；状态变更与发件箱同事务；订单侧消费事件完成履约。

## 1. 反转前后

| 维度 | 反转前（A 期影子态） | 反转后（P2） |
|---|---|---|
| 依赖方向 | payment → order（确认时直接改订单、发权益） | order → payment.api（订单消费支付事件） |
| 支付单 | 订单的影子副本（由订单同步写入） | **权威数据**，状态机在支付域 |
| 尝试/事件 | 通过 `order_id` 关联 | 通过 `payment_no` 关联（`order_id` 保留可空） |
| 订单 | 持有支付状态 | 只保留 `payment_no` 引用 |
| 跨域一致性 | 同步双写，进程崩溃会丢 | 事务性发件箱 + at-least-once 投递 |

## 2. 模型与不变量

- `t_payment_order`：`payment_no` 唯一，`(app_id, biz_type, biz_no)` 唯一；状态 CREATED → PAYING → PAID / FAILED / CLOSED，退款态 REFUNDING → REFUNDED / REFUND_FAILED。
- `t_payment_attempt`：只挂在支付单下（`payment_no`），`order_id` 可空仅作历史兼容。
- `t_payment_event`：回调幂等键 `(provider, event_key)`，`order_no` 存业务单号。
- `t_order.payment_no`：业务侧唯一支付引用，发起支付时写入、之后不再变。
- 业务单号（biz_no）与支付单号（payment_no）由业务侧生成规则耦合：本期 `P + orderNo`，多业务方接入时改为序列/雪花并迁移。

## 3. 四条链路的落点

| 链路 | 入口 | 行为 |
|---|---|---|
| 回调 | `payment/alipay/AlipayNotifyService` → `PaymentCallbackService` → `PaymentConfirmationService` | 验签 → 按渠道流水号定位支付单 → 去重/金额校验 → 改支付单 + 写 outbox |
| 模拟支付 | `order/OrderMockPaymentController` → `OrderPaymentService` | 仅测试用；与回调共用确认逻辑 |
| 主动查单 | `order/OrderPaymentReconciliationJob` → `OrderPaymentService.reconcile` | 扫“支付中的订单”向渠道查单，已支付则走确认 + 履约 |
| T+1 对账 | `payment/recon/ReconciliationService` | 我方支付单 vs 渠道账单，4 类差异（LOCAL_ONLY / PROVIDER_ONLY / AMOUNT / STATUS），差异处理台 |
| 退款 | `order/OrderRefundService` → 支付渠道 | 退款单写 payment 库，推进 `t_payment_order` 状态，订单侧改 REFUNDED |

## 4. 发件箱

- 确认服务在同一事务内 `INSERT t_payment_outbox`（PAYMENT_SUCCEEDED / PAYMENT_FAILED）。
- `PaymentOutboxDispatcher`：`PENDING → SENDING` 条件抢占 → 调监听者 → `SENT`；失败按 `base × attempts` 退避重试，超过 `max-attempts` 进 `DEAD`。
- 指标：`payment.outbox.in_flight`（积压）、`payment.outbox.dead`（死信）、`sent` / `failed` / `dead_lettered` 计数。
- 语义 at-least-once，监听者必须幂等。

## 5. 幂等

- 订单消费者 `OrderPaymentSettledListener`：订单已 PAID/FULFILLED 直接返回。
- 权益发放走 `t_student_series` 唯一键（`user_id + series_id`），重复事件不会重复发权益。
- 回调重复：`t_payment_event` 插入失败即判定重复，不再改支付单。

## 7. 证据（测试 ↔ 断言）

| 测试 | 断言 |
|---|---|
| `PaymentOutboxIntegrationTest`（3） | 确认即入箱；重复事件不重复发货（权益数仍 1）；消费失败退避重试后进死信 |
| `PaymentReversalIntegrationTest`（4） | 发起后 `t_order.payment_no` 有值、支付单 PAYING、尝试按 payment_no 关联且 order_id 为空；确认后支付单 PAID + 订单 FULFILLED + 运营快照可查；退款后双方 REFUNDED；outbox 指标已注册 |
| `PaymentConcurrencyIntegrationTest`（4） | 20 并发支付只产生 1 条尝试；20 并发重复回调只产生 1 条事件、1 条权益 |
| `ReconciliationIntegrationTest`（5） | 一致 → 0 差异；LOCAL_ONLY / PROVIDER_ONLY / AMOUNT / STATUS 四类差异；重复处理被拒 |
| `RefundConcurrencyIntegrationTest`（2） | 退款与履约竞态下终态 REFUNDED；并发退款幂等 |
| 架构 `ModuleBoundaryTest`（9 条） | 含 R5，构建可红 |

全量：单元测试 **128 通过**，集成测试 **36 通过**。

## 8. 已知遗留（不阻塞 P2 验收）

1. **主动查单仍在订单侧**：当前扫 `t_order`；下一步改为扫 `t_payment_order` 并把"过期关单"也交给支付事件，订单侧只做业务关单。
2. **确认的同步桥**：模拟支付路径仍同步回写订单（`OrderPaymentService#syncOrderAfterConfirmation`），生产回调已走事件；等主动查单反转后删除该桥。
3. **单渠道**：对账仅 MOCK；支付宝账单 API 未接入（需公网 + 商户密钥）。
4. **outbox 投递是本地监听者**：进程内投递，后续引入 RocketMQ 后投递器改为发送消息、消费端幂等相同。
5. **支付单号生成规则**耦合成 `P + bizNo`，多租户/多业务方上线前需迁移。
