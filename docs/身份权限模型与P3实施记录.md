# 身份与权限模型（P3 实施记录）

> 说明：文中角色/权限码为通用化示例；当前内核只内置 ADMIN 角色，垂直业务权限由各自业务仓定义。


> 日期：2026-11-18　范围：P3 身份通用化（角色/权限表化、接口权限码、邀请通用化、JWT 标准 claim）
> 结论：接口鉴权从"硬编码角色"切换为"权限码"；角色变成租户可配置数据，新项目接入只需建角色 + 授权限码，不改代码。

## 1. 为什么改

旧模型：`t_user.role` 一个字符串 + `@RequireRole("USER")` 注解，接口与角色名硬绑定。问题：

- 新项目/新角色必须改代码再发版；
- 同一角色无法细粒度控制（比如"能看订单但不能退款"）；
- 多角色用户无法表达。

新模型：**权限（permission）是代码契约，角色（role）是租户可配置的权限集合，用户可拥有多个角色。**

## 2. 数据模型（V18）

| 表 | 作用 | 关键约束 |
|---|---|---|
| `t_role` | 角色（ADMIN/OPERATOR/USER 或租户自定义） | `uk_role_tenant_code (tenant_id, code)`；`built_in` 保护内置角色 |
| `t_permission` | 权限点（如 `order:pay`） | `uk_perm_tenant_code (tenant_id, code)` |
| `t_role_permission` | 角色 → 权限 | `uk_role_perm (tenant_id, role_id, permission_id)` |
| `t_user_role` | 用户 → 角色（支持多角色） | `uk_user_role (tenant_id, user_id, role_id)` |
| `t_user_invitation.role_code` | 邀请携带目标角色 | 默认 `OPERATOR`，禁止邀请 `ADMIN` |

迁移做了两件事：插入内置角色/权限点/角色权限映射；按 `t_user.role` 回填 `t_user_role`。

## 3. 权限码目录（代码契约）

`PermissionCodes`（权限码常量目录，按域划分）：

- 内容/资源（垂直业务维护）：`catalog:read`、`group:read`、`progress:write`
- 订单/支付：`order:create`、`order:read`、`order:pay`、`order:cancel`、`payment:mock`
- 业务运营方：`operator:group:manage`、`operator:content:manage`、`operator:media:upload`
- 运营：`admin:user:manage`、`admin:order:manage`、`admin:group:manage`、`admin:invitation:manage`、`admin:recon:manage`、`admin:role:manage`

内置角色映射：ADMIN 全部；OPERATOR 运营三项 + 内容只读；USER 内容只读 + 订单四项 + 进度上报。

## 4. 鉴权链路

```
JWT(iss/aud/sub/tid/ver) → JwtAuthFilter 校验并设置 userId/tenantId → @RequirePermission("order:pay")
  → PermissionAspect → PermissionService（Caffeine 缓存，key=tenant:user，TTL 2min）
  → 权限码不匹配 → 403；匹配 → 进入业务
```

- 缓存显式失效：`RoleAdminService.assignRoles` / `updateRolePermissions` / 用户禁用时失效；TTL 只是兜底。
- 接口共 54 处注解从 `@RequireRole` 迁移为 `@RequirePermission`，旧注解与切面已删除。
- JWT 新增标准 claim `iss=btry`、`aud=btry-web`，解析时强制校验：跨系统/跨前端复用 token 会被拒绝。

## 5. 角色/权限管理 API（运营端）

- `GET /api/admin/roles`：角色列表（含权限码）
- `GET /api/admin/permissions`：权限目录
- `POST /api/admin/roles`：新建角色并授权（无需改代码）
- `PUT /api/admin/roles/{code}/permissions`：调整角色权限
- `PUT /api/admin/users/{userId}/roles`：给用户授角色

以上接口需要 `admin:role:manage`。

## 6. 邀请通用化

`POST /api/admin/invitations`（管理端）新增可选 `roleCode`：默认 `OPERATOR`，可邀请任意非管理员角色；接受邀请后用户以该角色入库并写入 `t_user_role`。邀请表为 `t_user_invitation`，语义已是通用邀请。

## 7. 兼容与迁移注意

1. **旧 token 全部失效**：iss/aud 校验上线后需重新登录（一次性，可接受）。
2. `t_user.role` 保留为"主角色"用于展示与兼容；**权限判定以 `t_user_role` + 角色权限表为准**。新用户创建/受邀注册会自动绑定。
3. 租户 0 的内置角色/权限由 V18 提供；其他租户暂复用租户 0 的角色定义（Pool 模式），真正租户隔离的角色配置在 SaaS 化时再做。

## 8. 证据

| 测试 | 断言 |
|---|---|
| `KernelIdentityIntegrationTest`（1） | 普通角色访问 `/api/admin/users` → **403**，管理员 → 200；通过 API 创建自定义角色 `AUDITOR*` 并赋给账号后立即生效——证明"不改代码即可定义角色" |
| `PermissionServiceTest`（2） | 权限按租户+用户缓存；`invalidate` 后立即重新加载——证明授权变更不依赖重启、缓存失效正确 |
| `JwtServiceTest`（3） | token 携带 tokenVersion；**错误 issuer/audience 被拒绝** |
| `UserInvitationServiceTest`（7） | 创建邀请校验角色存在、禁止邀请 ADMIN、接受后按邀请角色建号 |
| 单元/集成全量 | 单元 **133**、集成 **39** 全绿；9 条架构规则（平台层不得依赖业务模块）通过 |

## 9. 遗留

1. `RoleAdminController` 位于 operations.admin，直接依赖 `identity.rbac` 服务；按模块边界应收敛为 `identity.api` 契约（当前架构规则允许，属后续整理）。
2. 权限码尚无统一对外文档端点（`/api/admin/permissions` 已能列出目录）。
3. 角色删除/内置角色保护仅有字段，未提供删除接口（暂不需要）。
