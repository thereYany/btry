## 0. 这份文档要解决什么

诉求有三条，按优先级排：

1. **把「网课」做成可以替换的业务**，内核（登录、支付、存储、审计、监控）与业务解耦到「换一个项目只写业务代码」的程度；
2. **新项目能快速搭起来**：从脚手架到跑通登录 + 上传 + 支付，目标 ≤ 1 天；
3. **顺便练微服务**：不是一步拆完，而是抽一个服务做真实验证，且能随时回退。

V1 已经把「模块之间不互相 import 实现」做完了。V2 的战场换到三个地方：**业务语义、数据所有权、可复用产物**。

### 1.2 真正的耦合（按严重程度）

| # | 耦合事实 | 证据 | 为什么严重 |
|---|---|---|---|
| 1 | 支付表以业务订单为主键 | `V11__orders_payments.sql:60,86` `order_id`；`t_refund.order_id` `:105` | 支付单无法脱离「订单」存在，接第二个业务必须复制整套表 |

| 6 | 内容表承载定价 | `V11:1-6` `sale_status`/`price_cents`/`currency` 挂在 `t_series` | 内容域和交易域共用一个字段，未来做促销/多币种没有位置 |

## 2. 目标架构

### 2.1 三层

```text
┌───────────────────────────────────────────────┐
│  template（脚手架仓）                          │  新项目从这里 clone
└───────────────────────────────────────────────┘
                      ↓ clone & 改配置
┌───────────────────────────────────────────────┐
│  vertical（业务垂直包）                        │  catalog / order / entitlement
│  btry: course / learning / commerce / ops      │  learning / admin
└───────────────────────────────────────────────┘
                      ↓ 只依赖 kit 的 api + starter
┌───────────────────────────────────────────────┐
│  kit（内核，零业务词，starter 化）             │  web / identity / payment / media
│                                                │  notify / audit / observability
│                                                │  resilience
└───────────────────────────────────────────────┘
```

依赖规则（全部用 ArchUnit / Spring Modulith 强制）：

| 规则 | 说明 |
|---|---|
| R1 | kit 不得 import 任何 vertical（沿用现有规则） |
| R2 | vertical 之间只允许 import 对方的 `api` 包 |
| R3 | vertical 不得 import kit 的 `internal`/实现类，只用 kit 的 `api` 与 starter |
| R4 | 一张表只有一个 owner 模块；跨模块只引用 ID，不 join、不写 |
| R5 | payment 不得 import order / entitlement / course / identity |

R4 是新增的，也是最难的——它不能靠编译期检查，需要「数据所有权清单 + review」。

| 模块 | 来自现有代码 | 通用化动作 |
|---|---|---|
| `kit-web` | `platform/common/*`、`common/web/*`、`GlobalExceptionHandler` | 原样 |

| `kit-audit` | `platform/audit/*`、`aop/AdminAudit` | 操作码字典外置；operator 为空时改为显式告警而非静默跳过 |

| `kit-identity` | `identity/user`、`identity/auth`、`identity/security` | 角色/权限数据化；`@RequireRole` → `@RequirePermission`；JWT 补 `tenant_id/iss/aud`；白名单配置化 |

### 2.3 垂直清单（btry 业务）

| 模块 | 现状 | 处理 |
|---|---|---|
| `catalog` | `course/series` + `course/teacher` + `course/governance` | 保留；定价字段（`sale_status/price_cents/currency`）移到独立 `t_price` |
| `order` | `commerce/order` | 保留；去掉 `pay_channel`/`provider_trade_no`，只留 `payment_no` |
| `entitlement` | `commerce/entitlement` + `t_student_series` | 保留在垂直侧（「买了什么能看什么」是业务语义） |
| `learning` | `learning/playback` + `learning/learning` | 保留；播放授权改为调用 `kit-media` 的 `SignedUrlCache`，自己只做「有没有权限」 |
| `operations` | `operations/admin` + `operations/alert` | 保留；告警上报走 `kit-notify` |

### 2.4 数据所有权

| 表 | Owner | 其他模块可做什么 |
|---|---|---|
| `t_user`、`t_role`、`t_user_role`、`t_permission` | kit-identity | 只读 `id/username` 通过 api，不 join |
| `t_payment_order`、`t_payment_attempt`、`t_payment_event`、`t_refund`、`t_payment_outbox`、`t_reconciliation` | kit-payment | 只按 `payment_no` 查 api |
| `t_media_asset` | kit-media | 按 `assetId` 取元数据 |
| `t_series`、`t_series_chapter`、`t_series_video` | catalog | 只通过 api |
| `t_price` | catalog（或独立 pricing） | 只通过 api |
| `t_order` | order | 只通过 api |
| `t_student_series` | entitlement | 只通过 api |
| `t_learning_progress`、`t_playback_log` | learning | 只通过 api |
| `t_alert_log`、`t_admin_audit_log` | kit-notify / kit-audit | 只写不说 |
| `t_teacher_invitation` | identity 业务扩展 | — |

**落地手段**：把每张表的读写收敛到单一 `Repository`/`Mapper`，并给 `CatalogRepository` 这类跨域 SQL 开刀——它现在是「六表一个 SQL」，必须拆成「catalog 出商品 + entitlement 出是否已拥有 + order 出进行中订单」三次调用，在应用层拼装。

## 3. 支付解耦（V2 的核心）

### 3.1 目标模型

```text
[vertical: order]                         [kit: payment]
      │  createPayment(appId, bizType, bizNo, amount, subject, notifyUrl, metadata)
      ├───────────────────────────────────────────►  t_payment_order (status=CREATED→PAYING)
      │  ◄────────────── paymentNo + cashierUrl ───┤
      │                                            │
      │                          渠道回调 / 主动查单
      │                                            ▼
      │                          验签 → eventKey 唯一去重 → 状态机
      │                                            │
      │                          同一事务写 t_payment_outbox
      │                                            ▼
      │  ◄──── PaymentSettledEvent(paymentNo, bizNo, amount, channel, paidAt)
      ▼
  幂等履约（order: PAID → FULFILLED；entitlement: 发权益）
  失败进补偿队列；T+1 对账兜底
```

依赖方向彻底反转：**支付只发事实，业务自己履约**。

### 3.2 表设计（新增/改造）

```sql
-- 新增：支付单（独立的聚合根，不认识任何业务）
CREATE TABLE t_payment_order (
  id                BIGINT NOT NULL AUTO_INCREMENT,
  payment_no        VARCHAR(40) NOT NULL,
  app_id            VARCHAR(32) NOT NULL,        -- 多业务方接入
  biz_type          VARCHAR(32) NOT NULL,        -- vertical 自定义，如 COURSE
  biz_no            VARCHAR(64) NOT NULL,        -- vertical 的订单号
  subject           VARCHAR(128) NOT NULL,
  amount_cents      BIGINT NOT NULL,
  currency          VARCHAR(3) NOT NULL DEFAULT 'CNY',
  status            VARCHAR(20) NOT NULL,        -- CREATED/PAYING/PAID/FAILED/CLOSED/REFUNDING/REFUNDED
  channel           VARCHAR(20) NULL,
  provider_trade_no VARCHAR(64) NULL,
  notify_url        VARCHAR(255) NULL,
  metadata_json     VARCHAR(1024) NULL,          -- 业务上下文透传，支付永不解析
  expire_at         DATETIME(3) NOT NULL,
  paid_at           DATETIME(3) NULL,
  version           INT NOT NULL DEFAULT 0,
  created_at        DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at        DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_payment_no (payment_no),
  UNIQUE KEY uk_biz (app_id, biz_type, biz_no),          -- 幂等：同一业务单只有一个支付单
  UNIQUE KEY uk_provider_trade (channel, provider_trade_no),
  KEY idx_status_expire (status, expire_at)
) COMMENT='支付单';

-- 新增：事务性发件箱
CREATE TABLE t_payment_outbox (
  id           BIGINT NOT NULL AUTO_INCREMENT,
  event_type   VARCHAR(40) NOT NULL,
  payment_no   VARCHAR(40) NOT NULL,
  payload      VARCHAR(4000) NOT NULL,
  status       VARCHAR(16) NOT NULL DEFAULT 'PENDING',   -- PENDING/SENT/FAILED
  attempts     INT NOT NULL DEFAULT 0,
  next_at      DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  created_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_outbox_due (status, next_at)
) COMMENT='支付事件发件箱';

-- 改造：attempt / event / refund 的主键语义从 order_id 换成 payment_no
ALTER TABLE t_payment_attempt ADD COLUMN payment_no VARCHAR(40) NULL AFTER id;
ALTER TABLE t_payment_event   ADD COLUMN payment_no VARCHAR(40) NULL AFTER id;
ALTER TABLE t_refund          ADD COLUMN payment_no VARCHAR(40) NULL AFTER refund_no;
-- 回填后加唯一索引，保留 order_id 一版用于回滚

-- 改造：订单不再持有支付细节
ALTER TABLE t_order ADD COLUMN payment_no VARCHAR(40) NULL AFTER status;
-- 确认无读依赖后再 DROP pay_channel / provider_trade_no
```

### 3.3 端口与 SPI

```java
// kit-payment，入参只有支付概念
public interface PaymentPort {
    CreatePaymentResult createPayment(CreatePaymentCommand command);
    PaymentSnapshot query(String paymentNo);
    RefundResult refund(RefundCommand command);
}

public record CreatePaymentCommand(
        String appId, String bizType, String bizNo,
        long amountCents, String currency, String subject,
        String notifyUrl, Map<String, String> metadata) {}

// 渠道 SPI：不再接受 OrderRecord
public interface PaymentChannel {
    String code();                                  // ALIPAY / MOCK / WECHAT
    PaymentCreateResult create(PaymentOrder payment);
    PaymentQueryResult query(PaymentOrder payment, PaymentAttempt attempt);
    RefundResult refund(PaymentOrder payment, RefundRecord refund);
    NotifyPayload parseAndVerify(String rawBody, Map<String, String> headers);
}
```

关键变化：`PaymentGateway` 的 `OrderRecord` 入参换成 `PaymentOrder`（`kit-payment` 自己的聚合）。这样接第二个项目时，渠道适配器一行不用改。

### 3.4 一致性策略（这张表直接对应面试）

| 环节 | 手段 | 代码落点 |
|---|---|---|
| 下单幂等 | `uk_biz(app_id,biz_type,biz_no)` | 重复创建返回已有 `paymentNo` |
| 回调去重 | `t_payment_event.uk_payment_event_key` 插入即判重 | 沿用 `PaymentConfirmationService` 的 `inserted` 分支 |
| 金额校验 | `amount_cents` 与 `t_payment_order` 比对，不一致落 `FAILED` 事件 + 告警 | 沿用 `PaymentConfirmationService:40-53` |
| 状态机 | 单向流转，条件更新 + `version` | 沿用 `OrderTransitionPolicy` 思路，改为 `PaymentTransitionPolicy` |
| 事件不丢 | 同事务写 outbox，独立线程投递，失败重试 | 新增 `PaymentOutboxDispatcher` |
| 回调丢失 | 主动查单 job（已有 `reconcile`）+ 超时关单 | `PaymentService.reconcile` 迁移 |
| 履约失败 | 业务侧消费失败进补偿队列，可重放 | 新增 `t_payment_fulfillment_retry` 或在业务侧 |
| 最终对账 | T+1 拉渠道账单比对，差异落 `t_reconciliation` | 新增 `ReconciliationJob` |

**明确不做的**：2PC/XA、跨库事务、在回调里直接发 MQ（双写）。

### 3.5 迁移步骤（保证可回退）

1. **影子写**：新建 `t_payment_order`，创建支付单时同时写旧表结构，读仍走旧路径；跑 1 周对比数据一致性。
2. **切读**：`PaymentService` 改为读 `t_payment_order`，写双份。
3. **反向依赖清零**：`payment` 包删掉对 `order`/`entitlement` 的 import，履约改为发 `PaymentSettledEvent`，业务侧 `PaymentSettledHandler` 消费。
4. **停旧写**：观察 1 周无差异后，停写旧列；再加一版迁移 `DROP COLUMN`。
5. **回退方式**：`app.payment.legacy-write=true` 一个开关，保留旧路径代码到阶段 4 之后。

## 4. 媒体能力下沉（`kit-media`）

你说「视频不是优势」，那就别再让它当业务核心——把它变成可复用基础设施，反而是加分项。

| 能力 | 现状 | 目标形态 |
|---|---|---|
| 对象存储 | `CosPlaybackService` 直接 new COSClient，缺凭据就启动失败 | `ObjectStorage` 端口 + `CosAdapter` / `LocalAdapter` / `S3Adapter`；`@ConditionalOnProperty` 决定装配 |
| 直传 | `TeacherVideoUploadService` 把 `seriesId/chapterId` 编进 objectKey | `DirectUploadTicket`，key 由调用方给（`{appId}/{ownerType}/{ownerId}/{uuid}`） |
| 受保护 URL | `PlaybackUrlCache`，key 前缀写死 `btry:` | `SignedUrlCache`，前缀/TTL 配置化 |
| 元数据 | `t_series_video.media_status` 三态散在 Repository | `t_media_asset(id, object_key, size, mime, status, checksum, owner_type, owner_id)` |
| 消费进度 | `t_learning_progress`（视频语义） | 留在 vertical；kit-media 只给「资源」不定义「课程」 |

顺带修掉 §1.3 的 4 个正确性坑——下沉的组件会被复用，带病下沉等于放大 bug。

## 5. 身份通用化

1. **角色/权限落库**：`t_role(code,name)`、`t_permission(code)`、`t_user_role`、`t_role_permission`；`@RequireRole("ADMIN")` → `@RequirePermission("payment:refund")`，`RoleAspect` 的单角色全等改成集合匹配。
2. **业务角色外移**：`createStudent` 改 `createAccount(roleCode)`；`TEACHER/STUDENT` 的语义定义放到 vertical 的初始化数据里。
3. **邀请通用化**：`t_teacher_invitation` → `t_invitation(roleCode, tenantId, subject, token_hash, expires_at, status)`；如果不想动，至少修 `username` 长度不一致（`V7:9` vs `V1:4`）和缺 `(username,status)` 唯一约束。
4. **JWT 增强**：补 `iss/aud/tenant_id`，密钥强制从环境变量读（现在有默认值 `application.yml:42`），支持 key 轮换。
5. **白名单配置化**：`JwtAuthFilter` 里写死的 5 条路径（含 `/api/payments/alipay/notify`）改为 `app.security.public-paths` 配置。

## 6. 微服务方案

### 6.1 全景（要做就一次看清，但不要一次做完）

| 服务 | 数据 | 同步提供 | 异步发布 |
|---|---|---|---|
| edge（Nginx/网关） | — | 路由 + 鉴权 | — |
| identity-svc | `t_user`、`t_role`、`t_user_role` | token 签发/校验 | 账号事件 |
| payment-svc | `t_payment_*`、`t_refund`、`t_payment_outbox` | 支付/退款/查单 | `PaymentSettled` |
| catalog-svc | `t_series*`、`t_price` | 商品/定价 | 内容状态 |
| order-svc | `t_order` | 下单/订单查询 | `OrderPaid` |
| learning-svc | `t_student_series`、`t_learning_progress`、`t_playback_log` | 播放授权/进度 | 学习行为 |
| ops-svc | `t_alert_log`、`t_admin_audit_log` | 治理/告警 | — |

调用关系：

- 同步（强一致要求）：`order → catalog`（校验可售与价格）、`order → payment`（创建支付单）
- 异步（最终一致）：`payment → order`（支付结果）、`order → learning`（授权发放）、`learning → ops`（统计）
- 明确禁止：服务之间共享库、跨服务 join、同步链路里套 3 层以上调用

### 6.2 推荐路径：只抽一个（绞杀者模式）

**只把 payment 抽成独立服务**，其余保持单体。理由：

1. 它是唯一「边界清晰 + 数据能独立 + 能练到全部面试考点」的模块；
2. 单体能继续跑业务，风险可控；
3. 用端口双实现做到一键回退：

```java
// app.payment.mode = local | remote
public interface PaymentPort { ... }

@Component @ConditionalOnProperty(name="app.payment.mode", havingValue="local", matchIfMissing=true)
class LocalPaymentAdapter implements PaymentPort { /* 直接调 kit-payment 本地 bean */ }

@Component @ConditionalOnProperty(name="app.payment.mode", havingValue="remote")
class RemotePaymentAdapter implements PaymentPort { /* RestClient 调 payment-svc */ }
```

出问题改一行配置回退，不用回滚部署。这就是绞杀者模式（Strangler Fig）的最小形态。

### 6.3 抽 payment 要补的技术件

| 事项 | 选择 | 说明 |
|---|---|---|
| 服务间调用 | Spring 6 `RestClient` + 超时 + 重试 | 先不引 Feign/注册中心 |
| 注册发现 | docker compose 的服务名 DNS | 单机够用；要练就上 Nacos |
| 消息 | RocketMQ | 与 `docs/Redis降级与MQ边界.md` 的结论一致 |
| 鉴权 | JWT 公钥共享或网关校验 | 服务不互调身份接口 |
| 追踪 | 沿用 OTel，自动传播 `traceparent` | `TraceIdFilter` 已就绪 |
| 部署 | compose 多 1 个服务 + 1 个库 | 内存预算要算：现有 backend 640m，2C4G 最多再塞 2 个 256m 的 JVM |
| 回退 | `app.payment.mode=local` | 见上 |

## 9. 明确不做的事

| 不做 | 原因 |
|---|---|
| 现在全量拆微服务 | 单实例、无运维投入，拆了只会得到分布式单体 |
| 引入 2PC/XA | 渠道不支持，长事务锁死 |
| 为了「通用」提前抽象 | 只抽已经第二次用到的能力；`kit-entitlement` 标为可选就是这个意思 |
| 重写订单/课程表结构 | 影子写 + 渐进迁移，不做大爆炸 |
| 把 MQ 用在非资金链路 | 与 V1 结论一致，播放日志等用进程内队列足够 |
